# Environments for realtime LLM agents

Research date: 10 November 2026. Part 1 of the review; see [README.md](README.md) for scope and [solutions.md](solutions.md) for Part 2.

## How to read this file

**Play mode** (how the agent actually plays, checked in the paper or repo where possible):

- **Realtime-live (RL)**: the model picks actions during play and the environment clock runs while it thinks.
- **Paused-live (PL)**: the model picks each action but the environment waits for it.
- **Scripted (S)**: the model writes a program, policy, macro or input trace that then plays.

**Clock model** vocabulary used below:

- **WALL**: environment advances on real wall-clock time during inference.
- **TOKEN**: generated tokens are converted to environment time (reproducible, hardware independent).
- **INJECT**: environment is frozen during the call, then the measured latency is replayed into the simulation before the action lands (reproducible, charges model time but not network jitter).
- **BUDGET**: a fixed compute budget per tick, enforced by rule.
- **STEP**: environment advances only when the agent calls step (paused).

**Basis.** Every play-mode and clock label rests on a primary source that was opened and read: the repo's step loop ("code: <file>") or the paper's full text including appendices ("paper: <section>"). The Basis column gives the file or section and a short quoted phrase. Where a paper is silent and no code exists, the label is the one that follows from what the source does say, and the entry states what is missing. Items with nothing readable are listed under "Not reviewable" at the end. Numbers were extracted from arXiv HTML pages by a summarising fetch tool, not read off PDF tables; re-check any figure before quoting it in a paper. Model names from 2026 papers (for example GPT-6 Astra, Claude Opus 5, Jev) are reproduced as printed in those papers. Where an entry says "code read", the step loop was checked in a clone of the public repo on 10 November 2026 and the file path is given.

**Fit** is scored against the team's five preferences: realtime, verifiable, single player, human-easy, short horizon.

## 1. Realtime-live environments

### 1.1 Benchmarks built around a running clock for LLM/VLM agents

#### Realtime-Bench (Oct 2026)
- Tang, Yang, Zhang, Wang, Cheng, Zhao, M. Li, W. Li, Xia, Pei (UT Austin, Ohio State, UIUC, NVIDIA, Northwestern, Steadyworks). Paper [arXiv 2610.22155](https://arxiv.org/abs/2610.22155); code [RealtimeAgents/Realtime-Bench](https://github.com/RealtimeAgents/Realtime-Bench) (MIT).
- Tasks: 50 tasks, 30 web and 20 game, each with a programmatic success check. 20 are public (12 web, 8 game); the rest are held out. Public game tasks include timed chess (capture four pieces before a two-minute clock expires), Gomoku with ten seconds per move, Pong (return the ball six times), a 13-second timed route, and "survive 30 seconds on a collapsing highway". Public web tasks are operations workflows whose state changes mid-task (dispatch, seating, shipment regrouping).
- Play modes, per the repo's `docs/evaluation.md`: **wall clock** (default and leaderboard setting; observation, network, inference and action latency all count); **token clock** (time advances by output tokens / `tokens_per_frame`, 64 in the paper, so 64 tokens = 1 simulated second at 1 FPS); **paused clock** (one frame per action, action applies at the observed tick). Token and paused clocks need full provider token usage.
- Observation: screenshot at 1 FPS (768x432) plus a read-only Set-of-Marks list. Action: computer-use schema (click, type, key, drag, wait...). Single agent. Episode ends at the terminal condition or five minutes.
- Scoring: binary success, Pass^3 and Pass@k. No human numbers in the paper or the repo docs; tasks are described as "kept feasible for humans".
- Results (12 models: 7 standard, 3 realtime streaming, 2 decision models): best wall-clock success 44.0% and Pass^3 36% (GPT-6-Astra, high effort). Claude Opus 5 at high effort: 70% paused, 30% token clock, 14% wall clock. Gemini 3.8 Flash: 70% paused, 34% token, 32% wall. GPT-Realtime-2: 12-18% wall. Gemini 3.1 Flash Live: 6-18% wall. More reasoning effort helps when paused and is mixed or negative under a clock. Named failure modes: no temporal awareness, not tracking evolving state, misjudging when to act versus wait.
- Requirements: Linux, uv, Apptainer.
- Fit: realtime yes; verifiable yes; single yes; human-easy asserted by the authors but not measured; short yes. This is the closest existing work to the team's step 2, and the three-clock protocol is worth copying. Its gaps are the missing human baseline, the 1 FPS observation rate, and that half the tasks are GUI workflows rather than reflex tasks.

#### RealtimeBench and TORSI: "The World Won't Wait" (Oct 2026)
- Pan, H. Li, Shen, Ding, Tang, W. Zhang (Peking University, Samsung Research Beijing). [arXiv 2610.20665](https://arxiv.org/abs/2610.20665). No code URL yet. A different paper from Realtime-Bench above.
- Tasks: 180 tasks, six games x 30: Mario (platforming), Snake, Tetris, Temple (endless runner), River (steer and shoot), Bird (Flappy-style). Built on third-party open-source game implementations.
- Play modes: **paused**; **live** (game keeps running during inference, previous control stays active); **accelerated** (1.5x and 2x pacing). Each game declares its pacing, for example Mario 10 FPS, Snake 1.5 moves/s, Bird 20 FPS, River 60 FPS. It separates response latency (response time minus observation time) from action age (applied time minus observation time).
- Observation: structured text state built by the harness. Action: a legal action per game; several are short open-loop plans (Mario button plans, Tetris rotation + column, Bird one of eight flap schedules), so this is easier than pixels plus key presses.
- Scoring: progress normalised to 0-100 against a reference target per game; mean over six games. No human reference.
- Results (live average): GPT-6.1-sol 1.51 at about 19 s latency, against about 43.9 paused (the paused average was computed from the per-game table, not printed). Jev 13.51 at 0.52 s latency (about 28.3 paused), falling to 10.89 at 1.5x and 6.62 at 2x. StartLux 27B 16.62 was the best live score. So the ranking flips between paused and live.
- Fit: realtime yes; verifiable yes; single yes; human-easy in principle; short yes. Not usable until code is released.

#### Real-Time Reasoning Gym (RealtimeGym) (Nov 2025, ICLR 2026)
- Wen, Ye, Y. Zhang, Yang, Zhu (Stanford SALT and others). [arXiv 2511.04898](https://arxiv.org/abs/2511.04898); code [SALT-NLP/RealtimeGym](https://github.com/SALT-NLP/RealtimeGym) (MIT).
- Tasks: Freeway, Snake, Overcooked (scripted partner), each at three cognitive-load levels.
- Play mode: realtime-live. The environment steps once every N generated tokens (32k, 16k, 8k, 4k tokens per step are the pressure levels). If no action is ready the default applies (repeat previous direction, or idle). The repo also has `--time_unit seconds` for wall clock. The paper's wall-clock validation used steps of about six minutes, so the game is slowed to LLM speed, not run at human game speed.
- Observation: text. Action: one discrete move per step. 100 steps per episode. Scores normalised to 0-1. No human baseline. Only DeepSeek models in the main results, because the AgileThinker scaffold needs visible reasoning traces.
- Results: at medium load the planning agent (DeepSeek-R1) falls from 0.92 to 0.05 as pressure rises; the reactive agent stays flat but low; AgileThinker goes 0.90 to 0.58.
- Fit: realtime yes (simulated); verifiable yes; single yes; human-easy yes but unmeasured; short yes. Reusable: the token-clock harness, the two knobs (load and pressure), default-action-on-timeout, and three shipped agents.

#### ROAR (Oct 2026)
- Wang, Zhao, Yu, Zhou, Ma, Liu, Zhang, Chu, Koh, Ushaw, Davison (Newcastle University, University of Auckland, CTW Inc.). [arXiv 2610.24282](https://arxiv.org/abs/2610.24282); code [tb6147877/ROAR](https://github.com/tb6147877/ROAR) (MIT, prebuilt Unity executables).
- Tasks: Unity arena shooter with four levels: co-op (4 agents), competitive last-survivor, 2v2, and a basic single-agent level.
- Play mode: "Multi-Agent Asynchronous Gym". The environment and each agent run in separate threads; the environment advances every fixed interval without waiting for inference; a no-op applies if no fresh action is in the buffer. Tested at 250 ms and 40 ms ticks, plus a turn-based baseline. Code read (`roar_evaluation/async_env_runner.py`): the environment thread sleeps until `next_time` on `time.perf_counter()`, reads each agent's action buffer, calls `env.step`, then adds `step_interval` (default 0.04 s) to `next_time`. An action is consumed once; if none has been written since the last tick the default action is used. So the tick is enforced against the wall clock and the environment never waits for a model. The turn-based baseline is a plain `env.step(action)` loop (`roar_benchmark.py`, `start_run_turn_based`).
- Observation: RGB 512x512, depth, JSON text state, flat vector, and audio (sound-source list or raw mix). Action: 7-dim (move, yaw, pitch, fire, jump, minimap). 5-minute episodes. Score in 0-1. No human baseline; a heuristic bot and a random policy are the references.
- Results (turn-based / 250 ms / 40 ms): Gemini-3.1 Pro 0.87 / 0.44 / 0.34 (P50 latency 3.2 s); GPT-5.4 0.47 / 0.26 / 0.19; Gemma-4 31B 0.39 / 0.33 / 0.19; small local models (65-97 ms latency) about 0.07-0.10; heuristic bot about 0.33. Under realtime the best model is level with a rule bot. ReAct-style scaffolds help turn-based play but not realtime.
- Fit: realtime yes; verifiable yes; single-player level exists; human-easy plausible, unmeasured; short (5 min). The multi-channel observation (pixels, text, audio) matches the team's multi-channel hypothesis.

#### LOLPlay (Nov 2026)
- Zhaojian Yu. [arXiv 2611.03685](https://arxiv.org/abs/2611.03685); code [answers111/LOLPlay](https://github.com/answers111/LOLPlay) (read; no licence file). The repo README states "Gameplay continues during model reasoning and action execution".
- Tasks: 36 champion-specific tasks with 82 subgoal checks in the native League of Legends client (farming, development, sustain, combat, cooperation, map objectives), 5-20 minute budgets, at most 100 model responses.
- Play mode: realtime-live, wall clock. The paper states the environment keeps running while the agent generates and executes.
- Observation: 1920x1080 screenshots only. Action: mouse/keyboard, several actions per response. Scoring through Riot's Live Client Data API, which the agent cannot see.
- Human reference: two experienced players completed 36/36 (stated in the full text as a feasibility check, not a population estimate; the abstract does not mention it).
- Results: best task success 25.0% (GPT-6 Astra, low and medium effort), 16.7% at high effort; pooled 40 of 324 runs pass. Mean latency 6.5 s. Higher effort never improved task success.
- Fit: the closest published thing to "LLM plays DOTA". Realtime yes; verifiable yes; single yes; human-easy only for players who know the game; horizon too long for cheap training. Running bots on the LoL client may conflict with Riot's terms (not assessed).

#### GameWorld-RT (Apr 2026)
- Ouyang, Hu, Lin, Ng, Shou (NUS, Oxford). [arXiv 2604.07429](https://arxiv.org/abs/2604.07429); project [gameworld-bench.github.io](https://gameworld-bench.github.io). Code: [gameworld-project/gameworld](https://github.com/gameworld-project/gameworld) (read). The pause is a runtime flag, `pause_during_inference: bool = True` in `runtime/runtime_config.py`; GameWorld-RT sets it off.
- Tasks: 34 browser games in five genres (runner, arcade, platformer, puzzle, simulation), 170 tasks. Two interfaces: raw computer-use, or semantic actions through a deterministic parser.
- Play modes: the main benchmark is paused-live (the browser sandbox pauses the game during inference). GameWorld-RT keeps the game running (wall clock). RT was run only for two Qwen3-VL models.
- Scoring: state-verified through a JavaScript bridge exposing 233 game-state fields; success rate and normalised progress. Human reference under a 100-action budget: novice 55.3 SR / 64.1 PG, expert 77.1 / 82.6.
- Results: paused best is Gemini-3-Flash-Preview 21.2 SR / 41.9 PG at 5.5-12.8 s per step. RT: Qwen3-VL-235B 17.1 SR at 6.2 s/step; Qwen3-VL-30B 15.6 SR at 2.4 s/step.
- Fit: realtime yes (RT); verifiable yes; single yes; human-easy yes with measured humans; short yes. One of the best candidate pools, and RT mode is under-explored.

#### OmniGameArena (Jun 2026)
- Lin, Qian, Liu, Huang et al. (HKU, LIGHTSPEED, CUHK, Tsinghua). [arXiv 2606.09826](https://arxiv.org/abs/2606.09826); code [mxlin043/OmniGameArena](https://github.com/mxlin043/OmniGameArena) (read). The repo calls the two clocks LFM ("pauses the game during inference") and LCM ("charges model inference time to the game clock", `--clock lcm`, implemented in `omni_game_arena/clock.py`).
- Tasks: 12 new Unreal Engine 5 games: 7 solo (ObstacleRun3D, ObstacleRun2D, LastStand, MonsterShoot, SceneEscape, CueChase, SoloCraft), 3 PvP, 2 co-op.
- Play modes: PDQ (paused, main tables); LCRT (the simulator idles for the server-reported inference time before the action applies, an INJECT clock). LCRT was run for four models only.
- Observation: RGB frame + timestamp. Action: chunked keyboard-mouse. No human reference.
- Results: GPT-5.5 leads 4 of 7 solo games paused; under LCRT its SharedFloor score goes 0.368 to 0.048 and MonsterShoot drops by about 0.41, at about 16 s of model time per call. It includes two action models (NitroGen, Open-P2P) alongside frontier VLMs.
- Fit: realtime via injection; verifiable; 7 solo games; human-easy unmeasured; short.

#### VideoGameBench (May 2025)
- A. Zhang, Griffiths, Narasimhan, Press (Princeton). [arXiv 2505.18134](https://arxiv.org/abs/2505.18134); code [alexzhang13/videogamebench](https://github.com/alexzhang13/videogamebench) (MIT; you must own the games).
- Tasks: complete 1990s Game Boy and MS-DOS games (Doom II, Kirby's Dream Land, Zelda: Link's Awakening, Civilization I, Pokemon Crystal, three secret games, and others) from raw frames. Emulators: PyBoy, DOSBox/JS-DOS.
- Play modes: full = realtime-live (the game keeps running while the model thinks). Lite = paused-live (`--lite`; "the underlying emulator is paused whenever the agent is processing").
- Scoring: fraction of game completed, by perceptual-hash matching of frames to walkthrough checkpoints. No numeric human baseline.
- Results (v1): Gemini 2.5 Pro 0.48% full / 1.6% Lite; GPT-4o 0.09% / 1.6%. Both modes are near the floor, so the realtime gap is confounded with general failure.
- Useful extras: three practice mini-games (location clicking, mouse dragging, 2D navigation; 10 targets in 250 actions). Dragging was at most 10% for all models.
- Fit: realtime yes; verifiable yes; single yes; human-easy for early checkpoints only; short no.

#### PokeAgent Challenge, speedrunning track (NeurIPS 2025 competition; paper Mar 2026)
- Karten, Grigsby and others (Princeton, UT Austin). [arXiv 2603.15563](https://arxiv.org/abs/2603.15563).
- Task: Pokemon Emerald to the first gym, 15 milestones. Realtime-live: the paper states the game continues while the agent reasons; ranking is completion, then wall-clock time, then action count.
- Human reference: top speedrunner 18 minutes; average human 1:22:05.
- Results: winner 40:13 using LLM-written scripted sub-policies distilled into networks and refined with RL, so the model was not in the loop during play. Best pure-LLM harness 1:29:17. Raw VLMs without a harness about 0%.
- Fit: realtime yes; verifiable yes; single yes; human-easy yes; short no. Wall-clock time here is dominated by menus and navigation, not reaction. The lesson is that scripted routes win when allowed.

#### Win Fast or Lose Slow: StreetFighter (May 2025, NeurIPS 2025)
- Kang, Q. Zhang, Cai, Xu, Krishna, Du, Weissman (Georgia Tech, Berkeley, Harvard, Stanford). [arXiv 2505.19481](https://arxiv.org/abs/2505.19481); code [LatencySensitiveBench](https://github.com/HaoKang-Timmy/LatencySensitiveBench) (no licence file).
- Task: two locally served models fight in Street Fighter III on DIAMBRA. Each action occupies about 200 ms of game time; latency below 200 ms gives no further gain. Text observations, named moves, ELO over 40 matches per pair. Code read (`StreetFighter/GameEngine/Engine/game.py`): the main loop calls `env.step` continuously; any player with no action ready gets action 0 (no move), and actions are cleared after each step. Players run in separate processes and post actions to shared state. So a model that overruns simply stands still while the game goes on. The loop is not paced to a fixed frame rate; it runs as fast as the emulator steps, with a 1 ms sleep.
- Results: Qwen2.5-3B with FPX at 195 ms has the best ELO (5.99), ahead of 7B at 354 ms (2.33) and 1.5B at 142 ms (-1.25).
- Fit: realtime yes; verifiable (relative); not single player; human-easy yes; short yes. HFTBench from the same paper is under near neighbours.

#### LLM Colosseum (2024)
- [OpenGenerativeAI/llm-colosseum](https://github.com/OpenGenerativeAI/llm-colosseum) (MIT; user supplies the SF3 ROM). No paper.
- Two LLMs fight in Street Fighter III via DIAMBRA. Realtime-live, confirmed in code. In `eval/game.py` the main loop calls `env.step(actions)` continuously, filling in action 0 (no move) for any player without a pending action and deleting actions once executed. Each player has a `PlanAndAct` daemon thread that calls `robot.plan()` (the LLM call), then `robot.act()`, whenever its action slot is empty. In `agent/robot.py` the LLM is called only when the move queue is empty and one queued button is popped per step. The game therefore keeps stepping while a model is thinking. The loop is not paced to a fixed frame rate.
- Observation: text state or screenshot. Action: a short list of named moves expanded to button sequences (a macro layer). ELO over 546 fights: gpt-4o text 1912.5 top; Claude 3 Sonnet last at 1029.3 (latency and refusals).
- DIAMBRA also supports play against the built-in CPU, which would give a single-player absolute score.

#### Realtime Overcooked: HLA (2023) and DPT-Agent (2025)
- HLA: Liu, Yu, Gao, Xie, Liao, Wu, Wang (Tsinghua), AAMAS 2024. [arXiv 2312.15224](https://arxiv.org/abs/2312.15224). Overcooked with a human partner and chat at about 3 Hz, 100 s games, 60 volunteers.
- DPT-Agent: S. Zhang, X. Wang et al. (SJTU), ACL 2025. [arXiv 2502.11882](https://arxiv.org/abs/2502.11882); code [sjtu-marl/DPT-Agent](https://github.com/sjtu-marl/DPT-Agent) (MIT). Overcooked variant, 0.25 s per timestep, human and agent act simultaneously, 500 timesteps.
- Both are realtime-live. For DPT-Agent this is in code: `llm_agent_run_dpt_exp1.py` steps the game in a loop paced by `asyncio.sleep(0.25)` while the LLM modules run as separate async tasks. For HLA there is no code; the paper describes a game played "at a rate of approximately 3Hz" with a scripted executor acting while the LLMs run, and no pause. In both the LLM never issues atomic actions: a scripted executor or FSM does. DPT-Agent is partly scripted in this review's sense, since the LLM rewrites FSM code.
- Fit: realtime yes; verifiable yes; two-player by design; human-easy; short. DPT-Agent's harness is an open 4 Hz realtime Overcooked.

#### HAZARD with the Time Conversion Mechanism (2024 / 2025-26)
- HAZARD: Zhou, Chen et al., ICLR 2024, [arXiv 2401.12975](https://arxiv.org/abs/2401.12975): fire, flood and wind rescue in ThreeDWorld at 30 FPS. The original does not charge LLM thinking time: in `src/HAZARD/challenge.py` the agent chooses an action and only then is the environment stepped (`while self.env.controller.frame_count < self.max_steps`), so the simulator waits for the LLM (paused-live). The RRARA paper says the same of such benchmarks: "Many simulators effectively freeze the environment during model inference".
- RRARA: Zheng, Mao, Zhang, Cai (University of Sydney), [arXiv 2506.07223](https://arxiv.org/abs/2506.07223). Adds the Time Conversion Mechanism: frames advanced = ceil(inference seconds x FPS), with the agent standing still while the hazard spreads. Under it, GPT-3.5 (2.5 s) scores 0.25 value rate and Claude-3.7-sonnet (13 s) 0.07.
- Reuse: the conversion is a few lines and applies to any frame-based simulator.

#### Others with a realtime mode
- **GameVerse** (Mar 2026, Tsinghua), [arXiv 2603.06656](https://arxiv.org/abs/2603.06656): 15 games, paused by default; Snake and Plants vs. Zombies have Stop / Slow / Normal settings, where Normal is realtime. Reports that reasoning models drop sharply at Normal. Human rookie and expert tiers (37 participants).
- **GPTNT** (Jun 2026, TMLR), [arXiv 2606.28514](https://arxiv.org/abs/2606.28514): Keep Talking and Nobody Explodes with two agents under a live countdown; no tested model defuses a bomb in real time. Two modes (paper §4.1): "In asynchronous mode ... generation time per request counts against the bomb clock" (realtime-live) and "In synchronous mode ... the game is paused during generation" (paused-live). Code: [repo](https://github.com/GPTNT/gptnt) linked from the project page. Pairwise, so later-stage.
- **STAR** (Mar 2026), [arXiv 2603.09337](https://arxiv.org/abs/2603.09337): 1v1 hex wargame with turn-based and real-time modes; a thinking model falls from rank 1 to 17 in real time. The repo README defines the modes: "Real-time keeps the world ticking while the model thinks (latency changes outcomes); turn-based is the reproducible bench" (`starbench.py --mode turn_based|real_time`).
- **Orak StarCraft II ablation** (v3, Apr 2026), [arXiv 2506.03610](https://arxiv.org/abs/2506.03610): against the Hard built-in AI, paused scores of 75 / 100 / 100 (GPT-4o-mini, GPT-4o, Gemini 2.5 Pro) all fall to 0 unpaused, at 20-99 s per step. Section 5.7 says only that real-time gameplay was enabled; it does not describe the mechanism. The public repo (last commit June 2025, before the ablation) hard-codes `realtime=False` in `src/mcp_game_servers/star_craft/game/utils/bots.py`, so the realtime variant cannot be checked in code.
- **SIMA** evaluation environments (DeepMind, 2024), [arXiv 2404.10179](https://arxiv.org/abs/2404.10179): commercial games that "do not stop and wait while the agent computes"; tasks of about 10 seconds; not released. **Lumine** (2025), [arXiv 2511.08892](https://arxiv.org/abs/2511.08892): two regimes. The long main-storyline missions are realtime-live ("All the experiments are run in a real-time setting"). The 141-task benchmark is paused-live for every agent, Lumine included: "Since API responses can take as long as 30 seconds to return, we pause the game during inference following the setup in Cradle" (evaluation setting, which applies to "all agents"). Not an open environment. Both are covered in solutions.md.

### 1.2 RL-era platforms that are natively realtime

#### ViZDoom
- Kempka, Wydmuch, Runc, Toczek, Jaskowski, 2016; Farama. [Repo](https://github.com/Farama-Foundation/ViZDoom) (MIT); [competitions paper](https://arxiv.org/abs/1809.03470).
- `PLAYER` mode waits for the agent (paused-live). `ASYNC_PLAYER` advances at 35 tics/s without waiting; a slow agent misses frames. The tic rate can be changed, and the README lists time scaling in async mode, so the clock can be slowed for slow agents. The Visual Doom AI Competitions ran in async mode, so realtime play has been standard here since 2016. On missed tics the last button state persists: the engine polls the message queue without blocking in async mode (`viz_message_queue.cpp` `VIZ_MQTic`) and button state set by `setAction` carries over.
- Observation: screen, depth, labels (object segmentation), audio buffer, game variables. Each can be switched on separately. Action: button vectors and mouse deltas.
- Tasks: scenario WADs such as basic, defend_the_center, health_gathering, take_cover (from the bundled `scenarios/*.cfg`); custom scenarios are scriptable. Episodes last seconds.
- LLM use: "Will GPT-4 Run DOOM?" (paused); Game-TARS reports ViZDoom results (figures only); "Playing DOOM with 1.3M Parameters" ([arXiv 2604.07385](https://arxiv.org/abs/2604.07385)) reports a tiny classifier at 31 ms beating LLMs on defend_the_center (all agents, LLMs included, ran in ViZDoom `Mode.PLAYER`, `scripts/benchmark.py:95`, so the game waited for each LLM call; latency was measured, 0.6-13 s per decision, but not charged).
- Fit: 5 of 5. The strongest all-round base among classic platforms.

#### MiniWoB++
- World of Bits (Shi et al., 2017); MiniWoB++ (Liu et al., 2018); Farama. [Reward doc](https://miniwob.farama.org/content/reward/), [source](https://github.com/Farama-Foundation/miniwob-plusplus).
- Verified in `core.js`: the episode timer is wall clock with a 10 s default; positive reward is multiplied by max(0, 1 - elapsed/10 s); timeout gives -1. So it is realtime-live out of the box. Most LLM papers switch this off with reward processors (raw or binary reward) or longer timers, which makes their results paused-live in effect.
- Observation: instruction, structured DOM, screenshot. Action: click, drag, type. More than 100 tasks that humans finish in 1-3 s. Five tasks have no "no-delay" version and are inherently dynamic: chase-circle, moving-items, simon-says, button-delay, hover-shape.
- Fit: 5 of 5, and the cheapest realtime benchmark to stand up. Breakage: Selenium round-trip latency counts against the agent, and DOM serialisation is large.

#### FightingICE / DareFightingICE
- Ritsumeikan ICE Lab; IEEE CoG competition. [Repo](https://github.com/TeamFightingICE/FightingICE); [competition paper](https://arxiv.org/abs/2203.01556).
- 60 fps with 16.67 ms per frame, and observations delayed by 15 frames to simulate human reaction (rules page, saved; code `AIController.java` `DELAY = 15`). Rounds are 60 s. A sound-only track gives the agent only audio (48 kHz stereo, with FFT and Mel features). Blindfolded humans beat a weak MCTS AI in the sound-design protocol. On a missed frame the AI's previous input is reused (rules page: "AILoader will consider the AI's last input as a new input"). The repo has no licence file.
- Fit: realtime yes; verifiable yes; versus a fixed bot is effectively single player; human-easy; short. A rare open environment with an audio observation channel and a built-in reaction delay.

#### PySC2 and python-sc2
- [PySC2 docs](https://github.com/google-deepmind/pysc2/blob/master/docs/environment.md); [python-sc2](https://github.com/BurnySc2/python-sc2).
- Verified in source: `realtime=True` advances at 22.4 game loops per second, skips loops the agent misses, and (PySC2) records observation-to-action delays. Default mode is paused with `step_mul`.
- Mini-games (MoveToBeacon, CollectMineralShards, DefeatRoaches and others, listed in `pysc2/maps/mini_games.py`) are single-agent, about two minutes, and easy for novices.
- Fit: realtime via a flag; verifiable; single-agent mini-games; needs the Blizzard binary.

#### OpenAI Universe (2016)
- OpenAI, announced 5 December 2016. [Announcement](https://openai.com/index/universe/) (the page returns HTTP 403 to automated fetches, so its content here comes from search-result snippets and press coverage); [repo](https://github.com/openai/universe) (MIT, README read).
- Tasks: any program that can run behind a remote desktop. At launch: Atari games over VNC, Flash games, browser tasks (Mini World of Bits) and some PC games, described at launch as over 1,000 environments; the README says only "some environments include a reward signal". Exact counts are not given in the repo.
- Play mode: realtime-live. The README states that environments "run in real-time, rather than stepping synchronously with the agent's actions" and that "the environment keeps running in the background even if the agent does not call `env.step()`"; the agent cannot take thinking breaks.
- Clock model: wall clock. The game runs in a Docker container (the "remote") and the agent is a VNC client. A client-side throttle targets 60 fps (one frame every 16.7 ms) and sleeps if `step` is called faster. `reset` is asynchronous and returns empty observations until the environment is ready. The announcement reports driving dozens of environments at 60 fps with about 100 ms latency, mostly from server-side encoding. (The announcement page refuses automated fetches, HTTP 403; this figure is from its search-engine snippet. The play-mode label rests on the README.)
- Observation: screen pixels. Action: a list of VNC keyboard and mouse events, for example `('KeyEvent', 'ArrowUp', True)`, the same interface a human uses. Reward and diagnostics (including latency and client/remote timings in `info`) travel over a separate WebSocket channel.
- Players and horizon: single agent; short game episodes and browser tasks.
- Scoring and human reference: game score where a reward channel existed; no standard human baselines.
- Models evaluated: RL agents of the time (a starter A3C agent). No LLM results.
- Availability: archived on 6 April 2018, "deprecated in favor of the Retro library". It would not build today without effort.
- What went wrong: no official post-mortem was found. Gym Retro, its replacement, steps emulators synchronously with direct memory access instead of VNC, which removes exactly the realtime and remote-desktop parts. Reasons commonly given by users at the time, none confirmed in a primary source: results varied with network and encoding latency so runs were hard to reproduce, many environments had no reward or a noisy scraped one, and the Docker-plus-VNC stack was heavy to run at scale.
- What to take from it: it is the direct precedent for an agent playing over a realtime pixel-and-keyboard channel, and its design choices are still the right checklist. Keep the environment local to the agent to avoid network jitter. Log latency per step, as Universe did. Offer a deterministic clock (token clock or injected latency) next to the wall clock so results can be reproduced. Give every task a programmatic reward read from game state, not scraped from pixels. Keep a paused mode as a control. Expect that a realtime-only platform will be abandoned for a faster synchronous one unless realtime is the point of the benchmark.
- Fit: realtime yes; verifiable partly; single yes; human-easy yes; short yes. Not usable as code.

#### libmelee / Slippi; tmrl / rtgym; others
- **libmelee** ([repo](https://github.com/altf4/libmelee), now maintained at vladfi1/libmelee): Dolphin at 60 Hz reuses the last input, so a slow bot holds stale inputs. Structured state, no pixels. Firoiu et al. ([arXiv 1810.07286](https://arxiv.org/abs/1810.07286)) impose 12-15 frames of delay as human-like reaction. Needs a Melee ISO.
- **tmrl / rtgym** ([tmrl](https://github.com/trackmania-rl/tmrl), [rtgym](https://github.com/yannbouteiller/rtgym), both MIT): TrackMania at 20 Hz with an elastic wall-clock time step; the last actions are appended to the observation. Fits 5 of 5 in principle; needs the game client and a GPU. `rtgym` is a ready-made wall-clock wrapper for any step-locked environment.
- **Physical Atari** (Javed, Modayil, Kennickell, Sutton, Carmack, 2026), [arXiv 2606.19357](https://arxiv.org/abs/2606.19357): ALE free-running at 60 Hz, a robot at 30 FPS with about 165 ms latency. Evidence that unpaused Atari is a live research setting.
- **microRTS competition**: 100 ms compute budget per game cycle (rules page, saved). The game itself waits for `getAction` (`Tournament.java`) but overruns lose by timeout, so it is paused-live with a hard thinking budget.
- **CARLA**: default mode is asynchronous ("as fast as possible", not locked to wall clock); synchronous mode waits for the client.
- **Gran Turismo Sophy**: realtime only on PS4 hardware, 10 Hz control (paper: "GT Sophy interacted with the game at 10 Hz"; "Although GT ran only in real time"); interface not public.
- **Mineflayer**: the server runs in real time, but LLM agents on it mostly emit programs (scripted).

## 2. Paused-live environments, with convertibility

The common conversion is a wrapper that steps the simulator in a timer thread at its native rate and applies the agent's latest action, or a default, when no new one has arrived. `rtgym` implements this. What breaks in general:

1. Observation staleness becomes variable; observations need timestamps and the harness should log action age.
2. Scores depend on hardware and API latency. The fixes in the literature are a token clock, latency injection, or a fixed delay in frames.
3. The default action while thinking (no-op versus repeat-last) changes results a lot and must be specified.
4. Human reference scores for these games were collected in real time, so realtime model scores are the like-for-like comparison; paused scores are not.

### 2.1 Atari (ALE) and Atari-GPT
- ALE: Bellemare et al. 2013; Farama. [Docs](https://ale.farama.org/environments/). v5 environments use frameskip 4 and sticky actions 0.25. RGB or 128-byte RAM observations.
- Atari-GPT: Waytowich, White, Sunbeam, Goecks (US Army Research Lab), [arXiv 2408.15950](https://arxiv.org/abs/2408.15950). Seven games, frame skip 8, one model query per 8 frames, 2-7 s per call; authors say realtime was not possible. Human-normalised: GPT-4o 23.2%.
- Convertibility: high. Open source, microsecond step cost, 60 Hz native. Already run unpaused with RL: fixed action delays (Firoiu et al.) and Physical Atari. At 2 s latency a model misses 120 frames, so start with slow games (Freeway, Pong at reduced speed) or scale the clock and plot score against tick rate.
- Fit after wrapper: 5 of 5 with capped episodes (first to 5 points in Pong, one life of Breakout).

### 2.2 stable-retro, gym-super-mario-bros and LMGame-Bench
- LMGame-Bench: Hu et al. (UCSD, MBZUAI, Berkeley), ICLR 2026, [arXiv 2505.15146](https://arxiv.org/abs/2505.15146); [GamingAgent repo](https://github.com/lmgame-org/GamingAgent) (MIT). Super Mario Bros., Tetris, Sokoban, Candy Crush, 2048, Ace Attorney. Paused-live, confirmed in code: `lmgame-bench/single_agent_runner.py` loops `agent.get_action(...)` then `game_env.step(...)`, and the emulator advances only inside `step`. In the Mario environment (`gamingagent/envs/retro_01_super_mario_bros/superMarioBrosEnv.py`) the model's action string carries a frame count and `step` repeats the button press for that many emulator frames; inference time is logged (`time_taken_s`) but not charged. With harness, o3 scores Mario 3445, Tetris 42. No human scores.
- Convertibility: good for Mario and Tetris (NES at 60 fps; Tetris has gravity pressure). The puzzle games have nothing to convert. The harness's perception module (an o3 call per frame) would itself break under a clock.
- Orak uses gym-super-mario-bros and states it requires pausing.

### 2.3 V-MAGE
- Zheng et al. (CSU-JPG), [arXiv 2504.06148](https://arxiv.org/abs/2504.06148); [repo](https://github.com/CSU-JPG/V-MAGE) (no licence stated).
- Five pygame-style games, 30+ levels: FlappyBird, RaceGame, SuperMario, PongGame, Tempest Run. Pixels only. Explicit frame-pausing during inference; frames skipped per request is tunable. Human baseline from five participants. Models are far below humans even when paused (Race level 4: GPT-4o 22.9 against human 100).
- Convertibility: very good. Small Python games with their own frame loop. Because models are near random when paused, unpausing mainly adds a floor effect unless the game is slowed.
- Fit after conversion: 5 of 5.

### 2.4 Orak
- Park et al. (Krafton and others), [arXiv 2506.03610](https://arxiv.org/abs/2506.03610); [repo](https://github.com/krafton-ai/Orak) (MIT; six games need purchase).
- 12 games. The appendix states the game is paused during inference for Street Fighter III, Super Mario, StarCraft II and Stardew Valley. The StarCraft II pause is confirmed in code: `run_game(..., realtime=False)` plus an `isReadyForNextStep` event handshake between the bot and the environment process. Minecraft uses Mineflayer JavaScript. Observations are mostly text; actions are macros (Mario: only a jump level while Mario auto-runs).
- Convertibility: the pause is a harness addition and the authors' own ablation removes it for StarCraft II (scores to 0). Text state and macro actions make it a strategy-latency test, not a sensorimotor one.

### 2.5 StarCraft II family: TextStarCraft II, LLM-PySC2, AVA, SMAC, RTSGameBench
- TextStarCraft II ([arXiv 2312.11865](https://arxiv.org/abs/2312.11865)): text macro play. Paused-live for the built-in-AI experiments, realtime-live for the human matches, both from code. The repo URL in the paper (github.com/histmeisah/...) now holds an unrelated placeholder (three commits from 22 October 2026), but the original code is at [sc2musa/Large-Language-Models-play-StarCraftII](https://github.com/sc2musa/Large-Language-Models-play-StarCraftII) (commits by the first author; the HEP fork's pinned submodule commit resolves there). In it, `test_the_env.py:163` sets `--real_time` default False and `env/bot/Protoss_bot.py:2154` passes it to python-sc2 `run_game(realtime=...)`; `on_step` busy-waits for the LLM's action (`Protoss_bot.py:2001`), and python-sc2 only steps the game after `on_step` returns when not realtime. The human-match script `Human_LLM_agent_test.py:93` sets `--real_time` default True. The paper itself never says whether the game waits. LLM-PySC2 ([arXiv 2411.05348](https://arxiv.org/abs/2411.05348)): the step waits up to a maximum waiting time for all agents; "asynchronous" refers to parallel queries. AVA ([arXiv 2503.05383](https://arxiv.org/abs/2503.05383)): SMAC-like micro at "2 Hz"; paused-live from code (`multiprocess_run_env_with_ability.py`: blocking `get_action`, then `env.step`; `SC2Env` built without realtime).
- RTSGameBench (Kim et al., SNU, [arXiv 2606.18950](https://arxiv.org/abs/2606.18950)): Beyond All Reason; the game pauses between decision steps, one call per 15-60 s of game time. Human references on mini-games.
- Convertibility: SC2 has a verified `realtime=True`; SMAC-style micro battles are under two minutes with objective outcomes. The open Recoil engine behind Beyond All Reason is natively realtime. Units keep executing orders, so degradation under a clock is gradual for macro play and sharp for micro.

### 2.6 Cradle and its successors (CombatVLA, VARP)
- Cradle (Tan et al., BAAI and others), [arXiv 2403.03186](https://arxiv.org/abs/2403.03186): states it must pause RDR2 and Stardew Valley while waiting for the model; slow-paced management games run continuously. Actions are generated code functions. Later measured at about 62 s per decision.
- CombatVLA (Alibaba, ICCV 2025), [arXiv 2503.09527](https://arxiv.org/abs/2503.09527): states the game is paused during inference; 1.85 s per step.
- Convertibility: poor. Closed commercial Windows games, pausing through the game menu, human-judged success for Cradle. NitroGen's clock interception (below) is the practical route to controlling time in such games.

### 2.7 NitroGen universal simulator; Game-TARS and UI-TARS-2 sandboxes
- NitroGen (NVIDIA and collaborators), [arXiv 2601.02427](https://arxiv.org/abs/2601.02427): a Gymnasium wrapper that intercepts the game engine's system clock and "freezes the game while the model predicts"; real-time deployment is "left to future work". Released with weights.
- Game-TARS (ByteDance Seed), [arXiv 2510.23691](https://arxiv.org/abs/2510.23691): web games were run with time-pause "to ensure causal interaction" because of inference latency. UI-TARS-2 ([arXiv 2509.02544](https://arxiv.org/abs/2509.02544)): 15 browser mini-games, human-normalised scores. Paused-live: §2.2 says clients "receive synchronous observations" and the sandbox's "re-implemented Window timing APIs allow time acceleration and pause". Game-TARS's Minecraft (MCU) and ViZDoom runs use synchronous simulators (MineStudio; ViZDoom default `PLAYER`), so the whole suite is paused-live.
- Convertibility: the NitroGen wrapper can in principle freeze for a budgeted time or run at a fraction of real speed, giving a controllable clock on arbitrary Windows games. In code (`nitrogen/game_env.py`) the pause is the `async_mode` switch, "Whether to pause/unpause the game during each step", default True; turning it off leaves the game running, which is the 1x unpaused route. The ByteDance sandboxes are not released.

### 2.8 Overcooked family: Overcooked-AI, Collab-Overcooked, Robotouille, TimeArena
- Overcooked-AI (Carroll et al., [repo](https://github.com/HumanCompatibleAI/overcooked_ai), MIT): step-locked gym; its web demo runs human-AI games on a real tick.
- Collab-Overcooked ([arXiv 2502.20073](https://arxiv.org/abs/2502.20073)): step-based; humans under a 10 s per-step limit reach 90-100%, GPT-4o 4% at level 6. LLMs had no wall-clock limit.
- Robotouille ([arXiv 2502.05227](https://arxiv.org/abs/2502.05227)): "asynchronous" means in-game cooking delays, not model latency. ReAct GPT-4o: 47% synchronous, 11% asynchronous.
- TimeArena ([arXiv 2402.05733](https://arxiv.org/abs/2402.05733)): simulated action durations; model latency not counted. Tests multitasking as planning.
- Convertibility: easy. DPT-Agent already runs overcooked-ai at 4 Hz wall clock. A scripted partner makes it effectively single player. TimeArena converts by mapping simulated minutes to wall seconds.

### 2.9 Other step-locked platforms
- **Procgen** ([repo](https://github.com/openai/procgen)): 16 games, human rate 15 Hz, very fast simulator. 64x64 pixels are hard for VLMs and no text state is exposed.
- **Google Research Football** ([repo](https://github.com/google-research/football), archived): 100 ms per step; academy scenarios (empty goal, run to score) are single-player, under 40 s and easy. Sticky directions help as a default action.
- **Crafter / Craftax**: fast and text-renderable (Craftax glyphs), but not reflex-driven; a wall-clock tick would convert thinking into hunger and damage.
- **DeepMind Lab**: convertible but Linux-only with a Bazel build; ViZDoom covers the same ground.
- **MineRL / MineDojo / MCU**: 20 Hz synchronous stepping (code: MineRL `_multiagent.py` sync token and `TICK_LENGTH = 0.05`; MCU runs on MineStudio's vendored copy); a wall-clock wrapper works only if the simulator sustains 20 Hz. Heavy and long-horizon.
- **DIAMBRA Arena**: step-locked; LLM Colosseum is the existing realtime harness.
- **Flappy Bird** ([flappy-bird-gymnasium](https://github.com/markub3327/flappy-bird-gymnasium)), **PLE**, **MinAtar**, **PyBoy**: tiny, text-serialisable state, one or two buttons. Ideal for latency-versus-score curves. Riemer et al. ([arXiv 2412.14355](https://arxiv.org/abs/2412.14355)) already ran realtime Game Boy Pokemon and Tetris for RL.
- **Unity ML-Agents**: the route for building new realtime environments; ROAR and TowerMind are built on it.
- **TowerMind** ([arXiv 2601.05899](https://arxiv.org/abs/2601.05899)): open Unity tower defence with pixel, JSON and vector observations; ROAR is the same group's realtime follow-up.

### 2.10 Turn-based or untimed (contrast set)
All paused-live (turn- or step-based), each from its paper or code: BALROG (`balrog/evaluator.py`), SmartPlay (`examples/experiment.py`), FlashAdventure (paper §3.1, untimed by design), ARC-AGI-3 (docs: "ARC-AGI-3 games are turn-based environments"; scored on squared human-relative action efficiency), Kaggle Game Arena ([arXiv 2609.31473](https://arxiv.org/abs/2609.31473): poker "Each action has a 60-minute time limit"), CivRealm ([repo](https://github.com/bigai-ai/civrealm) step/turn loop), CivBench ([arXiv 2609.02459](https://arxiv.org/abs/2609.02459), "over 300 turns"), TALES ([arXiv 2504.14128](https://arxiv.org/abs/2504.14128), text games stepped per action), NetHack LE, SnakeBench ([repo](https://github.com/gkamradt/SnakeBench): "The simulation proceeds round-by-round"), StarBench ([arXiv 2510.18483](https://arxiv.org/abs/2510.18483), "A Turn-Based RPG Benchmark"), AgentBench's game tasks ([arXiv 2308.03688](https://arxiv.org/abs/2308.03688): Digital Card Game, Lateral Thinking Puzzles, House-Holding), GameBench ([arXiv 2406.06613](https://arxiv.org/abs/2406.06613): board games such as Santorini where "two players take turns"), GTBench ([arXiv 2402.12348](https://arxiv.org/abs/2402.12348): "randomly selects action at each turn" baseline, board and card games), BattleAgentBench ([arXiv 2408.15971](https://arxiv.org/abs/2408.15971): "a turn-based interactive game, Battle City"), GameArena ([arXiv 2412.06394](https://arxiv.org/abs/2412.06394): "each round's decision"), Think in Games (offline action prediction from Honor of Kings replays, not play) and the Pokemon stream harnesses. None has a native clock; a deadline could be imposed but the games do not reward reflexes. They are useful as the "same model, no clock" control and, for ARC-AGI-3, as a scoring template (human time over model time, squared).

### 2.11 SpeedrunBench online mode
The benchmark's main entry is in section 3 (its offline mode is scripted). The online mode is classified paused-live on this evidence:

- Paper, section 3.2: a game is defined as "a deterministic environment" in which "each action advances the game by one frame", and in the online setting, "given a current state of a game, the agent decides the next action". Game time is therefore a function of actions issued, not of elapsed time.
- Score: frames to the goal. The site states it "scores LLM agents on the number of frames needed to reach a goal state". Inference time is not part of the score, and no latency, pause or wall-clock handling is mentioned anywhere in the paper (main text and appendix), the site or the dataset card.
- Code: the open games are driven one logic step at a time. `DETERMINISM.md` in supertux-speedrun describes cancelling the browser main loop (`st_pause_main_loop()`) and having the harness call `st_tick()` once per step after applying that step's inputs, so the harness, not the clock, decides how many steps run.
- The only agent-in-the-loop environment code the authors released, `tools/tux_env.py` in tuxemon-speedrun, advances a fixed number of engine ticks per `step(action, hold=4, frames=8)` call and refuses to start unless `TUXEMON_DETERMINISTIC=1` ("Without it the engine runs on wall-clock").
- The GPT-5.6-sol online run is stored as a frame-indexed tape (`seeds/supertux/welcome_seed_9498f.json`, 257 keyed frames up to frame 9,498). At SuperTux's `LOGICAL_FPS = 64.0` (`src/supertux/constants.hpp:23`) that is 148.4 s of game time, with input changes as little as 16-31 ms apart, which a model running at maximum reasoning effort could only have produced in a game that waited for it.
- Which sentence governs: the introduction says the online agent acts "while the game runs", but the formal definition in §3.2 ("each action advances the game by one frame") is what the scores are computed under, the conclusion restates online as agents that "get frame by frame screen shots and must take an action", and every online result is a frame count (Opus 5 "160,021 frames"). The introduction's phrase contrasts acting within an episode with editing a whole trace; it does not describe a running clock.

What the sources do not contain: the online harness itself. The public repo (main, seven other branches and PR refs 1-15, history to depth 200) holds only the offline tape loop, scorers and agent cards; `sandbox/Dockerfile`, `.dockerignore` and `scripts/tas_decoding.sh` refer to unpublished files such as `scripts/pokemon_online_calib.py` and `sandbox/ONLINE_SPEEDRUN.md`. The Hugging Face dataset is gated (its public file tree lists only tapes, videos and metadata). So how many frames an online action is held, the emulators used for the commercial titles, and the exact online loop are not documented (the paper says only "the next action or short sequence of actions"). The site (a JavaScript app; its bundle was read) lets humans race recorded model runs and adds no technical detail on online play.

Convertibility: good for the three open-source games. SuperTux's stock main loop derives its step count from the wall clock (`SDL_GetTicks`), which is the realtime behaviour the benchmark patched out; running without `SUPERTUX_DETERMINISTIC`, or ticking `st_tick()` from a 64 Hz timer and applying the latest action, gives an unpaused online mode. Score would then be wall-clock time to goal, directly comparable to the human real-time records the paper already uses. SuperTux level 1-1 and one SuperTuxKart lap are short, single-player and human-easy. What breaks: bit-exact determinism (the reason for the patch), and at current latencies a platformer at 64 logic steps per second leaves a model hundreds of frames behind per decision, so a slowed clock or action chunks would be needed. The commercial titles would need their own emulators and ROMs.

### Framing papers from RL on modelling the clock
Each clock model below is taken from the paper's full text (saved and read).

- Ramstedt and Pal, Real-Time RL (2019), [arXiv 1911.04448](https://arxiv.org/abs/1911.04448): the action chosen at t takes effect at t+1; state is augmented with the last action.
- Bouteiller et al., RL with Random Delays (2021), [arXiv 2010.02966](https://arxiv.org/abs/2010.02966): random action and observation delays with an action buffer in the observation.
- Xiao et al., Thinking While Moving (2020), [arXiv 2004.06089](https://arxiv.org/abs/2004.06089): concurrent control, choosing the next action while the previous one executes.
- Firoiu et al., At Human Speed (2018), [arXiv 1810.07286](https://arxiv.org/abs/1810.07286): fixed frame delays on Atari and Melee with a predictive model.
- Riemer et al., Staggered Asynchronous Inference (2024), [arXiv 2412.14355](https://arxiv.org/abs/2412.14355): run overlapping inference processes so an action lands every tick.
- Anokhin et al., Handling Delay in Real-Time RL (2025), [arXiv 2503.23478](https://arxiv.org/abs/2503.23478): per-layer delay; MinAtar and MuJoCo.
- Li, Wang, Ramanan, Towards Streaming Perception (2020), [arXiv 2005.10420](https://arxiv.org/abs/2005.10420): scores the most recent finished output against the current world state, the ancestor of "action age".

## 3. Scripted environments, with convertibility

#### SpeedrunBench (Oct 2026)
- Fujinuma, Kamahori, Koike and others (Patronus AI, UW, Institute of Science Tokyo). [arXiv 2610.08076](https://arxiv.org/abs/2610.08076); site [speedrunbench.com](https://speedrunbench.com); [repo](https://github.com/patronus-ai/speedrun_bench); patched games [supertux-speedrun](https://github.com/patronus-ai/supertux-speedrun) and [tuxemon-speedrun](https://github.com/patronus-ai/tuxemon-speedrun); gated dataset of tapes and videos on [Hugging Face](https://huggingface.co/datasets/PatronusAI/speedrunbench).
- Games: Super Mario Bros., Super Mario Land, Mario Kart 64, Pokemon Blue/Red, Civilization I, Astray, SuperTux, Tuxemon, SuperTuxKart (the site says 10 titles and the dataset card also lists Wolfenstein 3D).
- **Offline mode: scripted.** A coding agent (via Opencode) writes a complete frame-indexed input tape each turn; a separate container replays it and returns the outcome and frame count; 200 turns. The README says "The agent never runs the game." Sub-settings: offline-scratch and offline-seed.
- **Online mode: paused-live** (see section 2.11 for the evidence). The agent sees the current frame and chooses the next action or short sequence; the score is game frames to the goal, not wall-clock time.
- Scoring: frames to goal as a percentage of the human world record (records are human real-time-attack runs).
- Results: offline with a per-turn scorer gets within about 7% of the record on SuperTux and about 3% on Super Mario Land. Online Pokemon Blue to the first badge takes about 4-12 times the record (Opus 5: 160,021 frames against about 40,435).
- Convertibility: see section 2.11.

#### Factorio Learning Environment (2025)
- Hopkins, Bakler, Khan. [arXiv 2503.09617](https://arxiv.org/abs/2503.09617). The agent writes Python programs in a REPL against the Factorio server. Out of scope by the team's rules, and Factorio has no reaction component.

#### Minecraft code agents: Voyager, Odyssey, MINDcraft
- Voyager ([arXiv 2305.16291](https://arxiv.org/abs/2305.16291); [repo](https://github.com/MineDojo/Voyager)) and Odyssey write Mineflayer JavaScript skills. Voyager pauses the server during LLM calls, confirmed in code: `voyager/env/bridge.py` calls `unpause()` before executing a skill and `pause()` after it, and `installation/fabric_mods_install.md` lists the Multi Server Pause mod as "used to pause the server when waiting for GPT-4 to reply". So Voyager is scripted with a paused world between skills. MINDcraft ([arXiv 2504.17950](https://arxiv.org/abs/2504.17950)) issues high-level commands on a live server.
- Convertibility: the server already runs at 20 TPS and at least one harness runs unpaused (Parallelized Planning-Acting, [arXiv 2503.03505](https://arxiv.org/abs/2503.03505)). To make latency bite, restrict actions to low-level controls and score survival time or kills in a short arena. The high-level API otherwise hides all sensorimotor difficulty.

#### Others
- **CodeClash** ([arXiv 2511.00839](https://arxiv.org/abs/2511.00839)): agents edit code between rounds; code competes. Out of scope.
- **PORTAL** ([arXiv 2503.13356](https://arxiv.org/abs/2503.13356)): the LLM writes behaviour trees.
- **Dota 2 bot scripting API**: Lua `Think()` called every frame; scripted natively. dotaservice exposes a gRPC step interface but is stale. 5v5, long, not human-easy: a motivating example, not a first environment.
- **PokeAgent speedrun winners** and **DPT-Agent's FSM** are scripted solutions inside realtime environments (see section 1).

## 5. Shortlist for the team's first environments

Ranked by fit against realtime, verifiable, single player, human-easy and short horizon, and by engineering cost.

1. **Realtime-Bench public tasks (run as is).** MIT, wall/token/paused clocks already implemented, single agent, five-minute cap, programmatic scoring. Use it as the external reference point and add the missing piece: a human baseline under the same wall clock. Weakness: 1 FPS screenshots and a GUI action space make it a test of slow reactions.
2. **MiniWoB++ with the original time-decayed reward.** Realtime out of the box, 10 s episodes, graded speed score, humans at 1-3 s, DOM text and screenshot channels. Include the five dynamic tasks that paused evaluations drop (chase-circle, moving-items, simon-says, button-delay, hover-shape). Cheapest to stand up and cheap enough to train on.
3. **ViZDoom basic scenarios in `ASYNC_PLAYER`.** Native 35 tics/s wall clock with adjustable tic rate, MIT, seconds-long episodes, and separately switchable pixel, depth, label, audio and game-variable channels, which suits multi-channel input experiments. Sweep the tic rate to get a score-versus-speed curve.
4. **A small arcade suite on a three-clock wrapper: Atari (Freeway, Pong, Breakout), Flappy Bird, V-MAGE games, SuperTux 1-1.** All open, short, single-player and human-easy, with human references (Atari human scores, V-MAGE players, speedrun records). Wrap with `rtgym` or the RealtimeGym harness and offer wall, token and paused clocks. Text-state variants (RAM, numeric features) allow a text-only model track alongside pixels.
5. **GameWorld-RT browser games.** State-verified scoring with novice and expert human baselines, short tasks, RT mode already exists but has been run on two models only. Depends on confirming the code release.
6. **RealtimeGym (Freeway, Snake, Overcooked).** Use as the training-friendly text environment: token clock gives reproducible rollouts for RL, and AgileThinker is a ready baseline. Add a human baseline and faster tick settings.
7. **ROAR single-agent level.** Open Unity build with pixels, text and audio, 40 ms and 250 ms ticks. The best fit for the "multi-channel input and output" hypotheses once the simpler environments are working.
8. **DareFightingICE versus a fixed bot.** Keep in reserve for an audio-channel task with a built-in 15-frame reaction delay.

Later, for pairwise work: DPT-Agent's realtime Overcooked, the UPenn deadline negotiation, GPTNT.

Design choices the evidence supports:
- Offer three clocks on the same tasks (wall, token or injected, paused). The paused score is the control that shows the failure is temporal.
- Collect human baselines under the same clock and interface. Almost no existing benchmark has them.
- Rule out scripted solutions by construction (no code execution, no offline trace editing), since they approach world-record times where live play is several times slower.
- Fix and report the default action, the tick rate, and action age.
- Include tasks whose answer is "wait" or "act at time T", since timing itself is where realtime API models score near zero.
